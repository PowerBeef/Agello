## Long-context digits on the GPU (LiteRT-LM #3913)

**Symptom.** On the iPhone GPU, Gemma 4 E4B started duplicating digits once a chat passed a few thousand tokens: "March 2026" became "March 202026". The CPU and 32-bit GPU activations were correct, so the app first worked around it by rebuilding the engine in float32 for long chats, at about half the decode speed.

**Root cause.** A device probe that copies a 48-digit number from increasing positions showed the errors start at exactly **position 2,048**. The model computes rotary angles from a float copy of the token position. With 16-bit activations that copy is float16, whose 11-bit significand holds every integer only up to 2,048; past it, positions round to even numbers and attention sees the wrong angle. The full analysis is [on the upstream issue](https://github.com/google-ai-edge/LiteRT-LM/issues/3913#issuecomment-6157362598).

**Workaround: patch the model file, not the runtime.** When this was found, the app ran Google's prebuilt runtime binary, so the fix edits the model file instead, which works on any runtime, ours included ([`patch_rope.py`](https://github.com/PowerBeef/agello-litert-lm/tree/main/tools/model-surgery)). It splits every position as `512·h + l`:

- `l` (0–511) goes through the model's existing MUL / SIN / COS;
- the phase of `512·h` comes from small precomputed tables selected with `onehot(h)`;
- angle addition combines them, using only values in [−1, 1].

Every float stays exact up to position 32,767. The first revision used 2,048-token blocks, the largest float16 allows; on M1-class GPUs the MUL / SIN / COS that follow also lose precision once the angle passes about 1,650 ([found on an M1 Max](https://github.com/google-ai-edge/LiteRT-LM/issues/3913#issuecomment-6166055004)), so the app now ships 512-token blocks: exact there too, replies identical to the 2,048-token file on the iPhone and the Mac, at the same speed. The weights are untouched, the main model and its speculative-decoding drafter are both patched, and the output is reproducible byte for byte from Google's file. A first attempt (shifting positions by −2,048) only doubled the exact range, to 4,096, which is why the split was needed.

**Results on iPhone 17 Pro**, with the first revision, on Google's LiteRT-LM v0.18.0 in October 2026 ([follow-up on the issue](https://github.com/google-ai-edge/LiteRT-LM/issues/3913#issuecomment-6159684389)):

| | Patched, float16 | Original, float32 (old workaround) | Original, float16 |
| --- | --- | --- | --- |
| Exact 48-digit copies, 0.7K–30K tokens | **14 / 14**, identical text to float32 | 14 / 14 | 0 / 3 |
| Prefill / decode at 8K tokens (tok/s) | **385 / 16.1** | 229 / 13.7 | 378 / 16.0 |
| Decode with speculative decoding at 16K (tok/s) | **34.7** | 17.1 | n/a |
| Memory after loading | **2.04 GB** | 2.76 GB | |

So every chat now runs at full float16 speed with no precision switch: 1.7–2.1× faster prefill, up to 2× faster decoding, 0.7 GB less memory, and no engine reload when a chat grows. The app downloads [the patched model](https://huggingface.co/PowerBeef02/gemma-4-E4B-it-litert-lm-fp16-rope), pinned to a commit; `test15_LongContextDigitFidelity` and probe 12 guard it.

**Credits, and the fix upstream.** The workaround came out of [the discussion on #3913](https://github.com/google-ai-edge/LiteRT-LM/issues/3913) with other developers:

- [@john-rocky](https://github.com/john-rocky)'s copy-fidelity suite first showed the errors growing with prompt length, on an M4 Max. Later runs by @john-rocky confirmed the patched files on that Mac and on a Pixel 8a's GPU. They also showed that a Gemma 4 E2B file exported with litert-torch's `odml.rope` composite is exact at float16 without any patch. That points to the proper fix being in the converter's export, requested in [litert-torch#1343](https://github.com/google-ai-edge/litert-torch/issues/1343).
- [@picitujeromanov](https://github.com/picitujeromanov) found the M1-class loss below position 2,048, and that 512-token blocks fix it.
- Google's LiteRT-LM team reproduced the issue.

Once a re-exported model or a runtime fix ships, the app can go back to Google's file (`agello-litert-update`, "When Google fixes #3913").

## A context window that never overflows

Overflowing LiteRT-LM's KV cache corrupts its native heap and crashes the app, so every message is budgeted before it is sent:

- **Count exactly.** The tokens already cached are read from the runtime, and the new message is counted with the model's own tokenizer as the runtime will render it (on a new conversation that includes the preamble, the tool schemas and the replayed history). Byte estimates, which count digits and ideographs as a token each, remain only where the tokenizer isn't available.
- **Fit or explain.** If the message plus a reply reserve doesn't fit, older turns are trimmed by token budget (the latest reply is truncated rather than dropped), relevant excerpts from evicted turns are recalled via EmbeddingGemma / BM25 (`KnowledgeBase.recallEvictedTurns`) and re-verified against `fitContext`, and the conversation is reseeded. A message that can never fit is rejected with an explanation instead of crashing.
- **Cap the reply.** The reply is capped to the room that's left. The preamble estimate includes the whole system prompt, personalization and project instructions included.
- **Tool budgets.** LiteRT-LM runs tool calls by itself while streaming, so a reply's room is split before it starts: the first round, where nearly every reply is answered, gets half the room with Think's reasoning budget on top; below 16K room, each tool result gets an eighth with at most 2 calls, and at `>= 16K` room (64K chats) each tool result gets a sixteenth (still 1,000–4,000 tokens) with up to 4 calls for multi-step Think + parallel read-only rounds (`withTaskGroup`), with later rounds sharing what's left and clamping post-tool reasoning via `ToolBudget.Plan.followUpThinkingBudget` so a Think turn never exhausts its follow-up cap without visible answer tokens. A streaming guard ends a reply cleanly before output plus tool results could overflow.
- **Context size.** The window isn't a setting. Devices with 11 GB of memory or more (the 12 GB iPhones; 12 GB is the app's floor since 2026-11-10) run at a fixed **64K (65,536 tokens)** using the shipped v2 model (`gemma-4-E4B-it-agello-v2.litertlm`: 1,536-slot local KV rings, 128K Dual-`GATHER` float16-exact rotary tables, `verify_8`). Each load measures the room the app has left and steps down to 16K below **4.2 GB** (`DeviceProfile.roomForLargeContextBytes`, recalibrated on 2026-11-22 and validated on iPhone 17 Pro with 0 memory warnings across 6.0 / 5.0 / 4.0 / 3.5 GB) and to 8K below 3.5 GB. Our runtime's global KV caches are Metal 4 placement sparse buffers (`MTLBufferSparseTier1`) trimmed immediately on reset/rewind, so memory follows what a chat fills rather than the window: on the iPhone 17 Pro on 2026-11-22, the v2 model at full 65,536 context held `3.18–3.45 GB` total footprint (`2.99–3.26 GB` free below jetsam) while passing 90/90 needle recall (21K–59K) and 12/12 bit-exact 48-digit copies up to position 65,534. Think's default reasoning budget is 4,096 tokens on every device since 2026-11-10.
- **Room for long answers.** With the on-device tools offered, a reply's room is split between generation rounds and tool results, and history trimming keeps a reply reserve free (`ContextBudget.replyReserve`): the answer share is capped at 4,096 tokens plus the reasoning budget (at most a third of the window), unlocking ~56,000–60,000 usable single-prompt tokens in a 64K chat without cutting long Think replies short.

## One engine, one conversation

`LiteRTChatEngine` (an actor) is the only code that touches LiteRT-LM's `Engine` and `Conversation`:

- **Serialized lifecycle.** Loads, settings changes, benchmarks, helpers and deletes run one at a time through `AppState.serialized`. The actor is reentrant across its long awaits; without the queue, two loads could interleave and hold two 3.7 GB engines.
- **Validated loads.** LiteRT-LM can report a successful load after failing to map parts of the model file. Each new engine must complete a one-token generation before use. Loads run on the GPU and fall back from multimodal to text-only; the last attempt is tried twice, and a load that still fails is reported (the CPU backend left the app on 2026-11-11: a reply at CPU speed wasn't a fallback worth having).
- **A bounded GPU cache.** LiteRT-LM's GPU cache makes a load take 0.8 s instead of 7.5 s, but it stores another copy of the E4B weights (each cache folder held about 2.5 GB) for every context size an engine is created with, in one file it never trims ([probe 14](../AgelloDeviceTests/WeightCacheProbe.swift)); one test run grew it to 10.25 GB and filled the phone. That was Google's binary. Our runtime keys the weights by content, so every context size shares one folder and one copy, named after the runtime's build; `EngineCache` deletes everything else in the cache root at the next load. The benchmark's one-off engine isn't cached, and EmbeddingGemma has a folder of its own.
- **Throwaway helpers.** Titles and memories use JSON-schema constrained decoding in a throwaway conversation with speculative decoding (MTP) on by default (fork `1382157b` + `7d80c7ec`, shipped in `agello-one-20261122-3`, fixed draft/verify grammar state sharing and multi-word `TokTrie` enums). On exclusive helper switches, `agello-one-20261122`+ detaches and restores the main conversation's sparse global KV caches with Metal 4 `MTL4CommandQueue.copyBufferMappingsFromBuffer:` (zero-blit page-table handoff; only the 1,536-slot local ring buffers blit on v2) when memory allows (`DeviceProfile.keepsConversationAcrossHelpers`); otherwise the chat's conversation is released before the helper and rebuilt from history after it, with `AppState.afterHelper()` always marking `conversationIsEmpty = false` so a failed or cancelled helper never leaks stale KV state into a brand-new chat.
- **Tool failures don't end replies.** LiteRT-LM v0.18.0 ends the whole reply when a tool call fails: a tool name the model invents, arguments that don't decode, or a tool that throws. Our fork's wrapper answers the call with an error the model reads instead, and the calculator returns its errors (with the syntax it accepts) rather than throwing. It takes what models write for money questions: `^` powers, `18%` percent, `$` and thousands separators.
- **No 10-minute stall after a dropped stream.** LiteRT-LM's Swift wrapper releases a stream's last reference to its conversation inside the native callback. When nothing else still holds the conversation (a stream abandoned early, or a conversation replaced while its cancelled stream was finishing), its deletion waits for the very task running that callback, and the engine stalls until LiteRT-LM's 10-minute timeout ([probe 9](../AgelloDeviceTests/ProbeScenarioTests.swift) waited 600 s for a first token). Our fork's wrapper holds the conversation weakly in the stream, so it's deleted where the app drops it, after its stream's work finishes, never inside the callback.
- **Stop and resume.** A cancelled conversation rejects the next message, so a stopped reply keeps its text and the conversation is rebuilt before the next send.
- **Settings apply when you send.** A setting changed just before sending, like **Think**, applies to that message. What a person can change (Think, the on-device tools, automatic search, personalization, a project, memories) only reseeds the conversation. The engine-level choices (the window, vision, audio, speculative decoding) aren't settings: the window is chosen as the engine loads, and a change to any of them, which only tests, probes and the Mac command line make, reloads the engine (`InferencePlanner.requiresEngineReload`).

## Branching conversations

Chat history is a SwiftData `VersionedSchema` with a migration plan (V1 → V3). Turns form a tree through `parentID`, and each thread's active leaf selects the visible branch. That is what makes edit, regenerate and the ‹ 2/3 › version switcher work. Regenerate and edit rebuild the model's context from the turns *before* the changed one, so abandoned versions never leak into the next answer. Migrations are tested against real on-disk stores, and a store that can't open is set aside rather than crashing the app.

## Retrieval with citations

Attached files are read with PDFKit and on-device Vision text recognition, split into ~400-token passages that keep their page numbers, and embedded in the background on the **16-core Apple Neural Engine** via Core AI (`CoreAIEmbedder`, 4-bucket asymmetric INT4 `EmbeddingGemma 2`, 768-dimension vectors stored in SwiftData as float16 and searched with vDSP — `0.86 s` for a 40-page PDF on iPhone 17 Pro with zero Metal GPU contention; `LiteRTEmbedder` on GPU and BM25 keyword ranking fill in as fallbacks). With more saved memories than a chat holds, each chat gets the 10 most recent and the 15 closest in meaning to its first message. `FileContext` decides what the model reads within half the context window: whole files, cited excerpts, or a cached section-by-section summary. Answers cite pages, like *(report.pdf, p. 23)*.

Web search follows the same shape: sources chosen by the message's topic (`SearchTopic`, named by the same planning call: Wikipedia and Wikidata, Wikivoyage, Wiktionary, Wikiquote, Apple Weather, Apple Maps, the ECB's rates, Crossref, PubMed, Wikipedia's Current events; since 2026-11-12 only sources whose terms permit the app, with no API key, every request identified as Agello), the message's language and English searched, five pages read in parallel with a random-nonce bounded readable-text extractor (`ReadableText.restoreCode`, preventing Billion Laughs expansion), resolved-IP SSRF guards (`getaddrinfo`) + `PublicRedirects`/`maxPageBytes` on every `WebClient` request, passages ranked on ANE with EmbeddingGemma 2, and numbered sources. Every untrusted external input (files, web results, shared text, external tool outputs) is spotlighted inside `<untrusted_data>` (`UntrustedContext.wrapFitted`, quarantined from persistent memories), and every mutating tool (`isReadOnly == false`) requires explicit approval via a fail-closed, request-ID-matched `ToolConfirmationCard` in both Chat and Voice mode. Search is a research step, not only a lookup, taken only when the message needs it: the same planning call first names the message's kind (chat, reaction, edit, creative, arithmetic, answered, question or request), and only questions and requests search, so skipping costs nothing and saves the reading and ranking. Asked yes or no instead, E4B skipped whatever it thought it could do alone, "How do I center a div with CSS grid?" included; naming a kind it gets right (`WebScenarioTests/test04`). The grammar holds the plan to its shape: one to three queries for a question or a request, none for the rest, and a follow-up's queries carry the conversation's subject. Otherwise the model plans one to three queries for what the message needs (for a question the facts that answer it; for a request to write, code or plan something, the techniques and APIs needed to do it well, and at most one complete example), EmbeddingGemma ranks the same 40-passage shortlist by each passage's best match to the message or one of those needs, code samples keep their lines and indentation through extraction and passage splitting, a request's sources take a third of the window rather than half, and the prompt presents the message as a request with the sources as reference. The bench, realistic requests sent through the app's own screens ([HARNESS.md](HARNESS.md)), judges changes like these.

## Language-agnostic tools and search

Gemma 4 E4B covers 140+ languages, but its highest instruction-following and tool-calling precision is in English, and proper nouns in English prompts can still pull helper outputs into another language (e.g. `"Is there a pharmacy near Place des Arts in Montreal?"` planned `"pharmacie près de Place des Arts, Montréal"`, which broke an English-only `" near "` splitter). Likewise, when a short CSV was inlined in Spanish, E4B skipped `query_table_or_json` and mis-summed mentally while calling the tool reliably for the same question in English.

Agello addresses this with a three-layer pattern that preserves zero-cost English speed and quality:

- **Structured tool schemas & canonical API formats.** `SearchPlacesTool` takes a separate `near` parameter alongside `query` (`PlaceSearch.search(what:near:limit:)`) so structured calls skip natural-language preposition parsing altogether. `WebContext.queryPrompt` keeps Wikipedia queries in the user's language while guiding structured API topics (`place`, `weather`, `currency`) toward canonical syntax with local place names kept intact.
- **Deterministic Swift defense-in-depth (`LanguageSupport.swift`).** All Swift-side parsers share one pure, zero-token helper covering 13 languages (EN, FR, ES, DE, IT, PT, NL, PL, RU, AR, JA, ZH, KO): current-location detection (`CurrentLocation.meansHere`), European + CJK reverse-order proximity splitting (`PlaceSearch.split`), weather and store-hours noise stripping (removing month names only when adjacent to numeric days/years and prepositions only at edges so `"Rio de Janeiro"` and `"La Paz"` stay intact), MapKit transport normalization, US + European localized number parsing (`$1,250.50` and `1 250,50 €`), and comparative follow-up detection (`WebContext.replansAsQuestion`), alongside multilingual currency/symbol parsing in `ExchangeRates` and diacritic/`ß → ss` folding in `UnitConverter`.
- **Zero-cost conditional grounding.** `SystemPrompt.base` stays compact and untouched. Only when `.csv`, `.tsv`, or `.json` files are attached does `FileContext.prompt` include a single-line hint before `Message:` directing the model to use `query_table_or_json` for calculations in any language — verified with natural French, Spanish, German, and English prompts naming no tools (`KnowledgeScenarioTests/test07_MultilingualNaturalToolIntent`).

## Memory, background and lifecycle

- **Memory limits.** The memory entitlements raise the app's limit to about 8.6 GB on a 12 GB iPhone 17 Pro and prevent address-space exhaustion when engines are rebuilt. A reply stops only when available memory falls below 400 MB, not at the first memory warning. The app's floor is 12 GB of memory. The memory suite simulates pressure on an iPhone 17 Pro with 6.0, 5.0, 4.0 and 3.5 GB usable, and every step passes in all four (the [roadmap](ROADMAP.md#current-status) has the dated runs); a load with less than 3.5 GB of room takes the 8K window.
- **Background GPU.** iOS doesn't allow GPU work in the background, so on backgrounding Agello synchronously acquires a `beginBackgroundTask` assertion, cancels in-flight generation (including intra-MTP, post-Think, active tool rounds, and in-progress `loadingConversation` init), and drains the GPU queue via `Conversation.waitUntilDone()` (`litert_lm_conversation_wait_until_done`) before iOS suspends the process. Eligible tasks (`BackgroundWorkPlan`: long document or multi-document synthesis, web research, and multi-step Think tool chains) run as a `nonisolated` `BGContinuedProcessingTask` (`submitTaskRequest`, iOS 27 API) with background GPU where supported (`onSubmissionFailure` immediately closes `GPUGate` and drains if backgrounded), and otherwise pause cleanly with a notice (`testBackgroundDuringGeneration` and `testLongSummarySurvivesBackgrounding` verify both paths on iPhone 17 Pro).
- **Extensions hand off.** Widgets, Control Center, Siri and the share sheet can't load a 3.7 GB model, so they hand their request to the app (App Intents, `agello://` links, and an App Group inbox for shared items).

## Model quirks we don't trust

- The model file reports *thinking* and *function calling* as unsupported, yet Gemma 4 reasons and calls tools on device; the app ignores those flags.
- Upstream LiteRT-LM's JSON-constrained decoding broke under speculative decoding (shared draft/verify grammar state) and rejected multi-word JSON enums (`▁` vs `0x20` in `LlgConstraintProvider`). Both are fixed in our fork (`1382157b` and `7d80c7ec`, with `AGELLO_JSON_MTP` enabled by default in `ChatEngine.swift`).
- Gemma 4 occasionally emits standard ASCII double quotes (`"..."`) or quoted keys inside FC tool calls on long expressions (`call:calculate{expression:"250 * ..."}`) instead of its native `<|"|>` delimiter, which upstream's generated ANTLR FC parser rejected. Our fork replaces the ANTLR FC parser (`8f9e7142`, shipped in `agello-one-20261122-3`) with a self-contained recursive-descent LL(1) parser in `fc_parser.rs` that cleanly supports paired `<|"|>` / `<escape>` / `ctrl46` verbatim strings alongside RFC 8259 JSON double-quoted strings and keys, fixes scientific notation with fractions (`1.5e-3`), guards recursion depth, and passes explicit `rust::Str(data, size)` slices across the C++/Rust FFI.
- When a background title or memory helper fails or is cancelled while keeping the active conversation (or before touching it), `AppState.afterHelper()` (`33db05e`) unbinds `conversationThreadID` and sets `conversationIsEmpty = false` so switching to a brand-new empty chat always reseeds cleanly and never inherits the previous chat's KV cache (`AppStateTests.testCancelledHelperDoesNotLeakContextIntoNewChat`).
